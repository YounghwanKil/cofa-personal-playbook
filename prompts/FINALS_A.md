# A: 분석과 구현

아래 블록을 과제 루트의 주력 세션에 붙인다.

```text
준비 자료 경로는 [절대 경로], 실제 과제 루트는 [절대 경로]다.
남은 작업 시간은 [분], 제출 마감은 [시각]이다.
공식 과제 지침을 최우선으로 해라. 준비 자료끼리 충돌하면 본선에서는
FINALS.md와 이 프롬프트를 START_HERE.md보다 우선해라.
너는 A 총괄이다. Worktree 기반 병렬 구현의 이득을 PLAN 단계부터 검토해라.
지금은 분석·계획만 수행한다. 내가 “구현 시작”이라고 하기 전에는
제품 코드·의존성·DB를 변경하거나 Worktree·구현 작업자를 만들지 마라.
공식 지침과 AGENTS, 현재 변경, 실행·제출 방법, 데이터 의미를 읽어라.
준비 자료 docs/FIELD_CHECK.md에서 실제 과제에 해당하는 항목만 적용해라.
반도체라는 말만으로 공정 제약·지표·과제 유형을 추측하지 마라.
과제 유형을 판단하고 불필요한 DB·웹앱·LLM을 추가하지 마라.

기존 계획 정본이 있으면 갱신하고 없으면 PLAN.md에 다음을 작성해라.
- 1쪽 요약: 사용자, 결정/불편, 필수 결과, 측정 가능한 성공 기준, 제외 범위
- 사실/가정/미확인 구분, 운영진 질문 최대 3개와 영향 범위
- 요구 ID별 수락 조건과 검사 입력/기대 결과
- 현재 구조와 첫 연결 흐름, 가장 단순한 기준선, 개선 가설
- 실제 데이터로 검증할 방법, 실패 사례, 제출 형식
- 시간 배분, 최소 완성 범위, 도구 장애 시 대안
- 공통 입력·출력·오류 형식과 인터페이스 계약
- 독립 작업별 담당, 수정 허용 파일, 의존성, 검증 명령, 완료 조건, 통합 순서
- 공통 스키마·의존성·락파일·마이그레이션의 단일 담당자
독립 작업은 최대 2개 워커를 기준으로 설계하고 A도 통합과 핵심 구현을 맡는다.
기능 이름만으로 분할하지 말고 실제 파일과 계약으로 독립성을 확인해라.
강하게 의존하거나 작업자/Worktree가 지원되지 않으면 순차 대안을 명시해라.
자유 선택이 허용될 때만 후보 최대 3개를 비교하고 하나를 추천해라.
자료 부족을 숨기거나 합성 데이터를 실제 사업 성과처럼 설명하지 마라.
15~20분 내 1쪽 계획 요약을 목표로 하되 시간 경과를 구현 승인으로 간주하지 마라.
```

계획 확인 후:

```text
구현 시작. 남은 시간은 [분]이다.
기존 계획의 필수 요구를 구현하고 작은 입력→결과 흐름부터 실제 실행해라.
효과 비교가 필요한 분석·예측·최적화 과제이면 기준선과 개선안을
동일 입력·동일 지표로 비교해라. 기능 구현 과제는 공식 수락 조건을 우선해라.
중단·세션 전환 시 .work/HANDOFF.md에 현재 상태, 실행 명령,
검사 결과와 다음 행동만 짧게 기록해라. 불필요한 기록 문서를 만들지 마라.
일반 구현 선택은 스스로 결정하고 중요한 범위 변경만 알려줘.
공식 요구는 지키며 미답변 질문에 의존하지 않는 작업은 계속해라.
PLAN의 인터페이스 계약을 확인하고 필요한 공통 골격을 먼저 준비해라.
공식 규정과 환경이 허용하고 이득이 있으면 독립 작업 최대 2개를 별도
Worktree/브랜치에 배정해라. A는 총괄·통합·핵심 구현을 계속한다.
미커밋 변경은 Worktree로 자동 전달되지 않는다. 기존 변경을 보존하고,
필요한 공통 코드가 기준 커밋에 포함됐는지 확인한 후 분기해라.
무조건 git add -A, reset --hard, 자동 stash로 기존 작업을 바꾸지 마라.
각 작업자에게 정확한 Worktree 경로·브랜치·기준 커밋·수정 허용 파일·
인터페이스·검사 명령·완료 조건을 전달하고 그 폴더에서 실행하게 해라.
Worktree 생성만으로 작업자가 생기지 않는다. 지원되는 서브에이전트를 배정하거나
사용자가 열 세션별 경로와 첫 프롬프트를 제공해라. 실행 상태를 추측하지 마라.
의존성 설치 위치·임시 DB·포트·출력을 분리하고 공유 파일은 단일 담당만 수정한다.
계약이 바뀌면 영향받는 작업자에게 반영을 확인해라. 작업자 추가 생성은 하지 마라.
작업자는 변경 파일·커밋·검사 결과·한계를 반환한다. A는 제출 루트에 한 작업씩
merge 또는 cherry-pick 중 한 방식으로 통합하고 중복 적용하지 마라.
충돌은 계약과 필수 요구를 기준으로 해결하고 통합 후 연결 검사를 실행해라.
개별 Worktree 성공을 제출물 성공으로 간주하지 마라. 통합·검증 전에
Worktree/브랜치를 삭제하지 마라. 순차 처리가 빠른 작업은 A가 직접 수행해라.
B는 통합된 고정 버전을 독립 검증하고 A가 수정·재검증한다.
B를 지원하지 않으면 A가 검증하되 독립 검증이라고 표시하지 마라.
첫 연결 흐름과 제출 전에는 실제 검사를 수행하되 별도 세션은 선택이다.
검토할 버전과 검사 명령을 기록해라. 수정 중지가 가능하면 같은 폴더를
검사해도 된다. 동시 수정이나 데이터 손상 위험이 있을 때만 격리 사본과
별도 DB/포트를 준비해라. 의존성 준비에 막히면 검증 범위를 명시해라.
마지막 약 20% 시간에는 선택 기능을 멈추고 제출 루트에서 최종 검사해라.
```

검토 반환 후:

```text
B의 REVIEW를 읽고 현재 버전과 비교해라. 재현되는 필수 결함부터 고치고
동일 입력으로 재검사해라. 취향 변경과 기능 확장은 뒤로 미뤄라.
새 검토 버전과 실행 결과를 HANDOFF에 남기고 C에게 설명 갱신 지점을 알려줘.
```
