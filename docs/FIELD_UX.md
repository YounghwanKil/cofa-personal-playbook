# 현업 분석 서비스의 요구 이해와 UX

이 문서는 특정 대회 문제나 실제 데이터를 설명하지 않는 일반 준비 지침이다. 실제 문제·데이터·현업 발언은 허용된 로컬 과제 환경에서만 읽고 이 공개 저장소에 기록하지 않는다.

## 현업 요구 이해

현재 업무 → 불편 → 필요한 판단 → 수락 조건으로 정리한다. 제공 자료의 사실과 자체 가정을 구분한다. 이미 자료에 답이 있는 것은 다시 묻지 않고, 결과를 바꾸는 핵심 질문만 확인한다.

- 사용자는 어떤 계기로 시작하고 무엇을 결정해야 하는가?
- 결과를 신뢰하려면 어떤 비교와 근거가 필요한가?
- 잘못된 판단과 누락 중 어떤 비용이 중요한가?
- 후속 확인·보고·공유 중 공식 요구에 포함된 것은 무엇인가?

## 화면의 일반 수락 조건

분석 범위·필터·단위·표본·데이터 시점이 명확해야 한다. 결과에서 해당 근거로 이동하고 다시 돌아올 수 있어야 한다. 빈 결과·오류·불충분 데이터·진행 중 상태를 구분한다. 순위나 상관을 검증된 원인이나 확률로 과장하지 않는다. 그래프와 표는 축·범례·단위를 표시한다. 실제 문제에 불필요한 요소는 추가하지 않는다.

## 서비스와 발표의 디자인 계약

A가 색상·서체·간격·상태·용어의 짧은 규칙을 정하고 W/H에 전달한다. W는 업무 조작과 판단을, H는 발표의 읽기 흐름을 우선한다. 스타일을 맞추려고 두 결과물의 런타임을 결합하지 않는다. 주장·수치·도식은 실제 제출 후보와 검증 근거에 맞춘다. 측정하지 않은 성능·시간 절약·만족도를 만들지 않는다.

디자인 확장보다 공식 요구·마감·보안 규칙을 우선한다. 검사 도구와 캡처 제한은 SECURITY_RULES.md를 따른다.
