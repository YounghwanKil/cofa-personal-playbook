# 배포는 무엇으로 했는가: 선택과 설명 준비

실제 과제 환경을 확인하기 전 특정 서비스를 정답으로 고정하지 않는다. **제공 미리보기로 충분한지, 외부 배포가 요구되는지부터 확인**한다. 아래는 선택 참고이며 이 키트를 배포했다는 뜻이 아니다.

## 상황별 선택

| 상황 | 우선 선택 | 설명할 한계 |
|---|---|---|
| 제공 앱과 미리보기·제출 경로가 이미 있음 | 제공 실행 방법 유지 | 프로세스·데이터 보존·접근 범위 확인 |
| 간단한 웹 UI와 짧은 API | 기존 풀스택 프레임워크 한 앱 | 계산 시간 한도·영구 저장 별도 확인 |
| Python 계산/데이터 처리 비중이 큼 | 제공 Python 앱 또는 FastAPI + 기존 UI | 서버 실행 수명·CPU 병목·DB 위치 |
| 긴 최적화·대용량 처리 | 장기 실행 워커 + 작업 상태 조회 | 작업 보존·재시도·중복·취소 구현 필요 |
| 외부 배포가 명시되고 계정·도구도 있음 | 익숙하고 확인 가능한 플랫폼 | 새 서비스마다 설정·네트워크·운영 비용 |

외부 클라우드가 필요하고 이미 사용할 수 있다면 웹 UI의 Vercel, Python API/워커의 Render, 영속 관계형 DB의 관리형 PostgreSQL 같은 조합을 검토할 수 있다. 다만 이것을 매번 세 서비스로 나누는 기본 처방으로 삼지 않는다. 한 앱으로 요구를 만족하면 그 편이 배포·설명의 경계를 줄인다.

Vercel 함수에는 실행 시간·메모리·요청 크기 등의 제한이 있다. 제한 숫자는 플랜·런타임·설정 변경에 따라 달라지므로 실제 환경에서 확인한다. 긴 작업을 요청 하나에 묶기 전 종료 한도와 실패 시 동작을 확인해야 한다. [공식 제한 문서](https://vercel.com/docs/functions/limitations)

Render의 기본 파일 시스템은 일시적이며 배포 시 로컬 변경을 잃을 수 있다. SQLite 파일을 로컬에 만들었다는 사실만으로 영속성을 확보했다고 말하지 않는다. 별도 DB/영속 디스크 등 실제 보존 경로가 필요하다. [공식 배포 문서](https://render.com/docs/deploys)

Render Background Worker는 요청을 직접 받는 웹 서비스와 달리 큐 등에서 작업을 가져와 처리하는 별도 서비스다. 워커를 배치하는 것과 작업 중복·실패 복구 정책을 구현하는 것은 다른 일이다. [공식 워커 문서](https://render.com/docs/background-workers)

## 질문에 답하려면 채워야 할 사실

| 질문 | 실제로 확인할 근거 |
|---|---|
| 어디에서 실행되는가? | 제공 환경 설명/실제 호스팅 프로젝트/접근 URL |
| 무엇이 앱을 실행하는가? | 실제 start 명령·진입점·포트 |
| 어떤 코드 버전인가? | 배포 커밋·이미지 태그·빌드 식별자 |
| 데이터가 어디에 남는가? | 실제 연결 DB·디스크·파일 경로와 재조회 |
| 서버 비밀 설정은 어디서 받는가? | 환경변수 이름과 주입 경로, 값은 노출하지 않음 |
| 프론트가 어느 API를 부르는가? | 실제 base URL과 브라우저 요청 |
| 계산이 어디서 실행되는가? | HTTP 핸들러/동일 프로세스 백그라운드/별도 워커 |
| 배포 후 무엇을 확인했는가? | health + 대표 입력 + 저장·재조회·실패 응답 |
| 되돌릴 수 있는가? | 이전 배포 선택과 DB 호환성 확인 |

`Dockerfile`, `render.yaml`, `vercel.json`이 있어도 실제 배포 성공을 증명하지 않는다. 반대로 이런 파일이 없더라도 플랫폼의 기본 프레임워크 감지나 관리 화면 설정으로 배포했을 수 있다.

## 흔한 말의 오류

- “Docker로 배포했습니다.” → 컨테이너가 실제로 실행되는 호스트/서비스를 덧붙인다.
- “Uvicorn으로 배포했습니다.” → 서버 프로세스와 실행 위치·접근 경로를 나눠 말한다.
- “Vercel에 다 올렸습니다.” → UI/API/계산/DB 중 실제로 무엇이 거기 있는지 확인한다.
- “DB를 썼으니 안 날아갑니다.” → 메모리 DB·임시 디스크·영속 DB는 다르다.
- “async니까 안 끊깁니다.” → 연결·플랫폼 수명·프로세스 재시작은 별도 문제다.
- “health가 200이니 정상입니다.” → 앱 시작 확인과 업무 흐름·DB 상태 확인을 구분한다.
- “CORS를 열어서 인증했습니다.” → CORS는 인증이 아니다.
- “코드를 롤백하면 끝입니다.” → DB 스키마와 저장 데이터의 호환성도 확인한다.

## 동기 처리로 충분한 경우

입력 상한이 작고, 최악의 처리 시간도 확인됐으며, 결과 복구가 중요하지 않은 짧은 작업이라면 동기 요청이 합리적일 수 있다. 이때 입력 크기 제한·시간 제한·오류 응답을 명확히 한다. 모든 과제에 Redis·Celery를 추가하지 않는다.

FastAPI의 BackgroundTasks는 응답 후 작업 기능이지만 무거운 계산에는 별도 도구가 더 적합할 수 있다고 공식 문서도 설명한다. 내구성·재시도·분산 처리를 자동 보장하는 기능으로 설명하지 않는다. [공식 설명](https://fastapi.tiangolo.com/tutorial/background-tasks/)

## 짧은 답변 연습

**제공 환경만 사용한 경우:**

> 제공된 [환경]에서 [명령]으로 실행하고 [미리보기 주소]에서 확인했습니다. 외부 클라우드로 추가 배포하지는 않았습니다. [데이터 위치]에 저장하며 [재시작 후 재조회 결과/미검증]입니다. 장시간 계산은 현재 [방식]이어서 [한계]가 있습니다.

**실제 외부 배포한 경우:**

> [UI/API]는 [플랫폼], DB는 [영속 서비스]를 사용했습니다. [커밋]이 [빌드/실행 명령]을 거쳐 실행됩니다. [주소]에서 [대표 입력→저장→재조회]를 확인했고, [제약]은 남아 있습니다. [개선]은 아직 계획입니다.
