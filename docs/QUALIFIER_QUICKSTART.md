# 예선용 과거 운영안 — 본선에서는 사용하지 않음

현재 본선 마감과 역할은 ../QUICKSTART.md를 따른다. 아래는 과거 예선 기록이다.

# QUICKSTART · 계획 먼저, 이후 3세션 운영

순서: **자료 받기 → A에서 분석·계획 → 내가 읽고 운영진 답변 전달 → 구현 시작 → B 검증 → A 수정 → C 기록 → 복습**.
처음에는 A만 열고, 계획을 확인한 뒤 B와 C를 연다. 세션 3개는 같은 제공 과제 루트에서 실행한다. 실제 시험의 도구·동시 세션 허용 범위를 우선한다. 지원하지 않으면 A가 역할을 순서대로 수행한다.

## 0. 과제 폴더 터미널

```sh
git clone --depth 1 https://github.com/YounghwanKil/cofa-personal-playbook.git .cofa-playbook
```

이미 있고 준비 문서를 수정하지 않았다면 `git -C .cofa-playbook pull --ff-only`. clone 폴더 안으로 이동하지 않는다. 제공된 Codex를 과제 루트에서 연다.

## 1. 세션 A: 처음에는 분석·계획만

아래를 복사하고 시간만 바꾼다. A는 이후 구현·통합 책임자도 맡는다.

```text
현재 폴더의 제공 과제가 대상이고 .cofa-playbook은 참고 자료다.
.cofa-playbook/START_HERE.md의 운영 규칙을 읽어라.
남은 시간은 [180분]이다. 지금은 분석·계획 단계다.
내가 “구현 시작”이라고 하기 전에는 제품 코드·의존성·DB를 변경하지 말고,
구현 에이전트·워크트리도 만들지 마라. 계획 문서 작성은 허용한다.

공식 README·AGENTS·요구사항·제공 데이터·기존 변경·실행/제출 방법을 깊게 분석해라.
전체 구조를 파악한 뒤 핵심 호출 경로·데이터 형식·단위·제약·기존 테스트를 집중 확인해라.
비밀값·생성물·의존성 디렉터리를 전수 출력하지 마라.
기존 실행·검사는 데이터 변경이 없는 격리 환경에서 가능한 범위만 확인하고,
실제 실행 관찰과 코드만 읽고 판단한 내용을 구분해라.

기존 계획 정본이 있으면 활용하고 없으면 과제 루트에 PLAN.md를 작성해라.
맨 위에 내가 읽을 1쪽 요약을 두고 다음을 정리해라.
- 문제·사용자·성공 기준·필수 요구 ID와 수락 조건
- 현재 구조와 입력→검증→처리→저장→결과 흐름, 근거 파일
- 확인된 사실·자체 가정·미확인, 알고리즘 후보와 선택 근거
- 검증 실패 데이터, 조건 변경, 계산 중 오류/DB 변경 처리안
- 첫 연결 흐름, 단계별 구현·검사, 배포/제출 확인 계획
- 워크트리별 담당 파일·공유 API/스키마 계약·의존성·통합 순서
- 위험·대안·미구현 범위와 남은 시간 배분

고객/운영진 질문은 내가 그대로 전달할 쉬운 문장으로 작성해라.
기존 자료에 답이 없는 중요 업무 질문만 Q번호로 한 번에 1~3개 제시해라.
질문마다 이유·답에 따른 차이·영향받는 작업을 붙여라.
일반 기술 선택은 네가 추천하고 이유를 적되 고객 확정으로 쓰지 마라.
내가 읽는 동안 독립적인 분석과 계획 보완은 계속해도 되지만 구현은 시작하지 마라.
마지막에 계획 위치·핵심 요약·운영진 질문·내가 결정할 사항을 제시하고 기다려라.
```

깊이는 문서 분량보다 **실제 파일 근거와 실패·변경 시 동작까지 설명 가능한가**로 판단한다. 예를 들어 180분 중 처음 20~30분을 분석·계획·읽기에 쓰는 것은 운영 예시이며, 무제한 분석하지 않는다. 시간이 지나도 자동 구현 전환하지 않는다.

## 2. 내가 계획 읽기 + 운영진 답변 전달

확인할 것은 ① 필수 요구가 빠졌는가 ② 데이터 의미·가정이 맞는가 ③ 최종 결과까지 이어지는가 ④ 작업 간 계약과 검사가 구체적인가다. 모르는 업무 규칙은 운영진에게 질문하고 답을 A에 전달한다.

```text
Q[번호]의 운영진 실제 답변: [답변 원문].
PLAN의 요구·수락 조건·가정·계약·검사 계획에 반영해라.
아직 계획 단계다. 제품 구현은 시작하지 마라.
변경된 부분과 남은 중요 질문만 알려줘.
```

## 3. 세션 A: 내가 준비되면 구현 시작

```text
계획을 확인했다. 구현 시작.
현재 남은 시간은 [분]이다. 확정된 범위를 PLAN에 따라 구현·검증해라.
미답변 업무 규칙은 가정으로 확정하지 말고 의존 작업만 보류해라.

너는 구현·통합 책임자다. 공통 API·스키마·설정·의존성 담당을 먼저 정해라.
필요한 공통 골격을 만든 뒤 독립 작업 최대 2개를 워크트리로 나눠
지원되는 서브에이전트에 배정하고 너도 핵심 구현을 계속해라.
강하게 의존하는 작업은 순서대로 처리해라.
워크트리의 기준 커밋·정확한 경로·브랜치·담당 파일·계약·완료 조건을 전달해라.
기존 미커밋 변경을 보존하고 관련 변경이 기준에 포함됐는지 확인해라.
환경이 지원하지 않으면 파일별 단독 담당 또는 순차 구현으로 대체해라.

작은 입력부터 최종 결과까지 첫 연결 흐름을 먼저 통합 검사하고,
나머지 필수 요구를 이어서 완성해라. 최종 검사는 실제 제출 루트에서 해라.

과제 루트의 .work/HANDOFF.md를 네가 관리해라.
현재 단계·작업 ID·담당·경로·상태·계약·검사 명령/결과를 적어라.
검토 가능한 묶음마다 고유 ID와 기준 커밋 또는 파일 지문, 변경 범위,
요구/수락 조건·재현 입력·테스트 명령·검토용 격리 경로를 남겨라.
B가 검토할 묶음은 고정하고 해당 사본을 검토 중 변경하지 마라.

.work/REVIEW.md의 새 지적을 작업 전환·통합 시 확인해라.
타당한 지적은 원 구현자가 수정하고 재검증한 뒤 HANDOFF에 처리 근거를 남겨라.
REVIEW와 PROJECT_DEFENSE는 직접 수정하지 마라.

완료·막힘·계약 변경은 즉시, 대략 5분마다 근거와 다음 행동을 알려줘.
검증과 기록 세션에 넘길 시점을 나에게 알려줘.
자료 저장소에 실제 과제 코드·기록을 올리지 마라.
```

A가 HANDOFF를 만들었다고 알리면 B와 C를 같은 과제 루트에서 연다. 세션 간 대화는 자동 공유되지 않는다. **파일 작성이 다른 세션을 자동 실행시키지도 않는다.** 네가 아래 명령으로 각 세션을 시작하거나 다시 깨운다. 5분 보고도 백그라운드 예약 실행을 보장하는 것은 아니다.

## 4. 세션 B: 검증 전담

```text
너는 검증 세션 B다. 제공 과제 루트에서 작업한다.
.cofa-playbook/START_HERE.md와 PLAN, .work/HANDOFF.md를 읽어라.
제품 코드·PLAN·HANDOFF·PROJECT_DEFENSE는 수정하지 마라.
네가 편집할 기록은 .work/REVIEW.md뿐이다.

HANDOFF에서 검토 준비가 된 고정 묶음을 확인해라.
기준이 불명확하거나 구현 중인 파일뿐이면 검토 가능한 기준을 요청해라.
현재 작업 중인 DB·서버에 쓰지 말고 격리된 테스트 경로·임시 DB·포트를 사용해라.
요구 충족·계산 오류·검증 실패 데이터 차단·조건 변경·중간 실패·저장 보존을 확인해라.
실제 검사 명령과 결과, 실행하지 못한 항목을 구분해라.

지적마다 검토 ID·기준 버전·요구 ID·심각도·파일:줄·재현 조건·
기대/실제 결과·수정 제안을 REVIEW에 적어라. 추정은 추정으로 표시해라.
수정은 A에게 맡기고 다음 검토에서 같은 사례로 수정 여부를 확인해라.
검토가 끝나면 A에 전달할 짧은 요약을 나에게 주고 기다려라.
```

B가 끝나면 **A에**:

```text
B가 .work/REVIEW.md를 갱신했다. 검토 기준과 현재 코드의 차이를 확인해라.
타당한 지적을 담당자에게 수정시키고 관련 검사를 다시 실행해라.
처리 결과와 다음 검토 기준을 HANDOFF에 남겨라.
```

A가 수정한 뒤 **B에**:

```text
HANDOFF의 새 검토 묶음으로 이전 지적의 수정 여부와 영향 범위를 재검증해라.
REVIEW에 기준 버전과 실제 검사 결과를 갱신해라.
```

## 5. 세션 C: 기록·설명 전담

```text
너는 기록 세션 C다. PLAN·.work/HANDOFF.md·.work/REVIEW.md와
실제 코드·변경·검사 근거를 읽고 과제 루트의 PROJECT_DEFENSE.md만 관리해라.
기존 설명 정본이 있다면 그 파일을 쓰고 위치를 알려줘.
제품 코드와 다른 세션의 문서는 수정하지 말고 검사·서버를 중복 실행하지 마라.

.cofa-playbook/docs/핵심질문7개.md를 중심으로 배포 설명까지 정리해라.
현재 동작·선택 이유·실제 파일/함수·검증과 수정 사례·가정·한계를 짧게 연결해라.
작업자의 보고와 직접 확인한 근거를 구분하고, 근거 없으면 미확인으로 표시해라.
참조한 검토 ID/버전과 작성 시점을 남기고 이후 코드가 바뀌면 재확인 필요로 표시해라.
계획을 구현 완료로, 과거 검사를 현재 버전 검증으로 바꿔 쓰지 마라.
기록이 끝나면 내가 읽을 핵심과 불일치만 알려주고 기다려라.
```

중요 통합이나 수정이 끝나면 **C에**:

```text
최신 HANDOFF·REVIEW·실제 코드로 설명 기록을 갱신해라.
핵심 7문항과 배포 설명만 유지하고 중복 예상 질문을 늘리지 마라.
```

## 6. 마지막 15~20% 시간: 최종 확인과 복습

**A에**:

```text
남은 시간은 [35분]이다. 선택 기능 확대를 멈춰라.
남은 필수 요구와 큰 결함을 우선 처리하고 제출 루트에서 최종 흐름을 확인해라.
최종 검토 묶음과 실제 실행·저장·제출 확인 항목을 HANDOFF에 남겨라.
미완료·미검증을 숨기지 마라.
```

순서대로 B에 최종 재검증 → 필요하면 A 수정 → B 재확인 → C 최신 기록 갱신을 요청한다. 제출 절차에 필요한 시간을 남기고, 설명 준비 때문에 필수 결함을 방치하지 않는다.

허용된 사전 연습 시간에 **C에**:

```text
핵심 7문항과 배포 설명을 현재 구현에 맞춰 한 개씩 질문해라.
정답과 힌트를 먼저 보여주지 말고 내 답을 기다려라.
내 답을 실제 코드·검증 근거와 대조해 틀린 주장과 빠진 한계를 알려줘.
```

새 세션으로 이어갈 때는 역할(A/B/C)과 PLAN·HANDOFF·REVIEW·설명 정본 경로를 전달한다. 구현 시작 여부도 HANDOFF로 확인한다. 실제 Q&A 단계의 AI 제한은 해당 회차 규정을 따른다.
