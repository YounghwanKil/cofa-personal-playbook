# 입장 직후 세팅 · 프롬프팅 · 에이전트 운영안

> 이 문서의 외부 키트 설치는 대안 비교다. 이 저장소의 기본 경로는 루트 README → START_HERE.md이며, 외부 키트를 추가 설치할 필요가 없다.

## 추천 결론

**메인 1명 + 필요할 때 독립 구현자 1~2명 + 체크포인트 검토자 1명. 기록 전담은 기본 구성에서 뺀다.** 처음에는 메인이 최소 흐름을 직접 연결하고, API·데이터 구조가 안정된 뒤 독립 작업만 나눈다. 메인은 통합·요구 판단·공통 기록의 주인이다. 검토자는 완성된 변경 묶음과 마지막 통합본을 읽는다.

이 인원·시간 제안은 공개 지침과 사용자의 기존 방식을 토대로 한 내 판단이다. 실제 시험 성과로 검증한 최적 인원은 아니다. 자원이 적거나 작은 문제면 메인 하나와 마지막 독립 검토만으로 줄인다.

## 기존 방식에서 유지할 것과 바꿀 것

| 기존 방식 | 판단 | 변경안 |
|---|---|---|
| 폴더를 깊게 분석 | 유지하되 범위 제한 | 파일 지도→입력/실행 진입점→핵심 흐름 순서. 모든 파일을 끝까지 읽고 시작하지 않기 |
| 단계별 Markdown 계획 | 유지 | 요구 ID·완료 조건·담당 파일·의존성까지 있는 짧은 계획 하나 |
| 기능별 워크트리·서브에이전트 | 조건부 유지 | 먼저 공유 계약 확정. 독립 편집 경계가 생긴 뒤 최대 2개 구현 작업부터 |
| 5분마다 진행 보고 | 유지하되 짧게 | 메인이 모아서 완료/실행 근거/막힘/다음 작업만. 실패·계약 변경은 즉시 |
| 구현 후 피드백 에이전트 | 유지·시점을 앞당김 | 첫 핵심 흐름이 돌면 한 번, 통합 완료 뒤 한 번. 계속 실시간 감시하지 않기 |
| 피드백을 구현자가 재수정 | 유지·종료 조건 추가 | 메인이 요구 위반인지 분류→원 담당자가 수정→검토자가 해당 항목 재확인 |
| 기록 전담을 따로 둘까? | 기본적으로 불필요 | 구현자가 근거를 반환하고 메인이 공통 기록에 반영. 마지막에만 문서-코드 일치 검토를 맡기기 |

OpenAI 공식 설명도 서브에이전트는 독립적인 읽기·탐색 작업에서 시작하고, 동시 코드 편집은 충돌과 조정 비용을 주의하라고 안내한다. [공식 Subagents 설명](https://learn.chatgpt.com/docs/agent-configuration/subagents)

## 입장 직후 0~10분

공식 과제 폴더를 작업 루트로 유지한다. 아래 명령은 템플릿이며 도구가 없는 경우 설치부터 하지 말고 제공된 대안을 확인한다.

```sh
pwd
git status --short
rg --files -g 'AGENTS.md' -g 'README*' -g 'package.json' -g 'pyproject.toml' -g 'requirements*.txt' -g 'Dockerfile*' -g 'compose*.yml' -g 'render.yaml' -g 'vercel.json' -g '!node_modules' -g '!vendor'
python3 --version
node --version
```

기존 변경 파일·기존 AGENTS·공식 실행 방법·제출 위치를 먼저 확인한다. 기존 앱을 한 번 실행하고 대표 입력을 넣어 본다. 이때 실제 미리보기 주소와 데이터 저장 위치를 기록한다. 전역 도구 업데이트·MCP 대량 설치·새 모델/API 연결을 초기 세팅에 넣지 않는다.

### 선택 A: COFA 키트를 미리 연습했다면

내가 우선 고르는 것은 [leey00nsu/cofa-hackathon-kit](https://github.com/leey00nsu/cofa-hackathon-kit)이다. 요구 확인·검증뿐 아니라 현재 코드에 근거한 문답 준비까지 이어진다는 점이 이번 요구에 가장 가깝다. 설치기 원문에서 `--matt core/all/none` 옵션을 확인했다. 여기서는 `core`만 제안한다.

**먼저 현재 README·설치 코드와 기존 AGENTS 처리 방식을 확인하고, 적용할 범위를 결정한 다음 실행할 명령:**

```sh
# 공식 과제 루트에서. 같은 이름의 폴더가 있으면 재사용 여부부터 확인.
git clone --depth 1 https://github.com/leey00nsu/cofa-hackathon-kit.git .hackathon-kit
python3 .hackathon-kit/scripts/kit.py --help
python3 .hackathon-kit/scripts/kit.py install --workspace . --matt core
```

클론은 원격 최신 상태를 받는다. 조사 때 확인한 커밋은 [공개 레포 조사](01-공개레포조사.md)에 있다. 시험 전 리허설 때 한 버전을 골라 동작을 확인하고, 당일 업데이트에 시간을 쓰지 않는 편이 좋다. 이 조사에서는 설치기와 일부 스킬·규약을 읽었으며, 설치·전체 테스트를 실행해 호환성을 검증하지는 않았다.

스킬이 실제로 발견된다면 채팅에서 해당 키트가 안내하는 이름을 호출한다. 발견되지 않으면 경로를 지정해 필요한 문서를 읽게 한다. **하위 폴더로 clone한 것만으로 그 안의 모든 지침이 상위 과제에 적용됐다고 생각하지 않는다.** Codex 공식 로컬 탐색 경로는 실행 위치부터 저장소 루트까지의 `.agents/skills`이며, 제공 버전의 지원 여부는 현장에서 확인한다. [공식 스킬 문서](https://learn.chatgpt.com/docs/build-skills)

### 선택 B: 처음 보는 도구에 시간을 못 쓰면

새 프레임워크를 설치하지 않고 아래 시작 프롬프트를 쓴다. 기록은 `PLAN.md` 하나와 `PROJECT_DEFENSE.md` 하나로 시작한다. 기존 기록이 있으면 그 파일을 재사용한다. 필요할 때만 계획에서 태스크 ID를 늘린다.

가벼운 공개 참고는 [hamjoon2003/sk-hynix-2nd-harness](https://github.com/hamjoon2003/sk-hynix-2nd-harness)의 TASK·DECISIONS·서술형 문서다. 여러 키트의 AGENTS를 동시에 겹쳐 적용하지 않는다.

## 첫 프롬프트: “깊게 분석해”를 이렇게 바꾼다

```text
이 과제는 제한시간 안에 동작하는 결과와 그 구현을 설명하는 것이 목표다.
먼저 공식 README·AGENTS와 기존 변경을 확인하고 제공 스택을 유지해라.

1. 파일 지도를 만든 뒤 입력 데이터·실행 진입점·핵심 처리·저장·화면 연결만 우선 추적해라.
   의존성/생성물/큰 원본 전체를 읽지 말고 필요할 때 해당 부분을 조사해라.
2. 사용자·입력·최종 결과·필수 제약·성공/실패 기준을 정리해라.
   확인된 사실, 우리가 정한 가정, 구현을 바꾸는 미확인을 구분해라.
3. PLAN.md에 요구 ID, 수락 조건, 작은 구현 단계, 담당 파일, 의존성,
   검사 방법을 적어라. 기존 계획이 있으면 갱신해라.
4. 먼저 가장 작은 입력→처리→최종 결과 흐름을 실제로 실행해라.
   업무 규칙이 불명확해 결과가 달라지는 부분만 질문하고, 독립 작업은 계속해라.
5. 기술적이고 되돌릴 수 있는 선택은 이유를 기록하고 진행해라.
   기능 완료마다 재승인을 요청하지 마라.

아직 모든 기능을 워크트리로 나누지 마라.
첫 흐름과 공통 데이터/API 계약을 확인한 뒤 독립 작업만 병렬화하자.
현재 남은 시간은 [실제 분]이다. 분석·설정이 길어지면 작은 실행을 우선해라.
```

핵심은 분석의 깊이를 낮추는 것이 아니라 **처음에 필요한 근거와 나중에 읽어도 되는 자료를 구분**하는 것이다. 시간 제한 없는 전수 분석은 금방 큰 문맥을 만들고 구현 시작을 늦출 수 있다.

```text
현재 PLAN의 의존성과 공통 계약을 기준으로 독립 작업만 나눠라.
메인은 핵심 흐름·통합·공유 스키마·공통 설정·전체 상태 기록을 맡아라.
필요할 때 구현 서브에이전트를 최대 2명까지 사용해라.

각 작업에는 요구 ID, 목표, 읽을 파일, 편집 허용 파일, API/데이터 계약,
완료 조건, 실행할 검사, 변경 금지 범위, 반환 형식을 줘라.
서브에이전트는 추가 서브에이전트를 만들지 마라.

공통 계약 변경이 필요하면 메인에 영향과 대안을 보고하고, 독립 부분을 진행해라.

워크트리는 실제 Git·제출 경로·환경이 지원하고 격리 이점이 있을 때만 써라.
공유 작업공간이면 파일 소유 범위를 나누고, 공통 문서는 메인만 갱신해라.
완료/막힘은 즉시 보고하고, 메인은 대략 5분마다 상태를 한 번에 요약해라.
```

### 좋은 분할과 나쁜 분할

| 분할 | 병렬화 판단 | 이유 |
|---|---|---|
| 입력 검증 로직 + 고정 계약을 쓰는 결과 표 | 가능 | 파일과 계약이 분리됨 |
| 알고리즘 개선 + 별도 파일의 실패 사례 조사 | 가능 | 검토는 읽기 중심, 구현은 단독 편집 |
| 서로 다른 원인의 테스트 실패 두 개 | 가능 | 원인과 수정 파일이 분리된 경우 |
| 백엔드가 응답 스키마를 만들면서 프론트가 추측 구현 | 보류 | 스키마 변경마다 재작업 |
| DB 마이그레이션 + 같은 모델을 여러 작업자가 수정 | 순차 | 공통 데이터 계약이 흔들림 |
| 스캐폴딩 직후 각자 패키지를 추가 | 보류 | package/lockfile·설정 충돌 |
| 모든 에이전트가 프로젝트 전체를 깊게 분석 | 피함 | 중복 읽기와 서로 다른 전제 |

### 작업자에게 줄 최소 작업 계약

```text
Task: T03 / 요구 R02
목표: 입력 용량이 허용 범위를 벗어나면 구조화된 오류 반환
편집: src/validation.py, tests/test_validation.py만
참조: PLAN.md의 R02와 현재 입력 스키마
계약: validate(payload) -> ValidatedInput / ValidationError
조건: 0·음수·상한·상한+1·결측을 요구 정의대로 처리
금지: 공통 모델·DB·의존성 변경, 다른 작업자의 파일 수정
검증: 실제 검사 명령과 결과. 못 돌렸으면 미검증
반환: 변경 파일, 관련 요구, 선택 이유, 검사 결과, 한계,
      커밋(격리 작업 시), 아직 필요한 연결
```

## 워크트리는 격리 장치이고, 통합은 별도 일이다

워크트리를 쓰면 작업자에게 **정확한 경로와 기준 커밋**을 준다. 에이전트의 대화 문맥이 분리된 것과 파일 시스템이 분리된 것은 서로 다르다. 실제 경로·브랜치·파일 소유를 확인한다.

- 공유 스키마·패키지 설치·마이그레이션은 메인 소유로 고정한다.
- 격리된 작업자의 커밋을 메인이 검토한 뒤 통합한다. 통합 방식을 하나로 정한다.
- 미커밋 파일은 다른 워크트리로 자동 전파되지 않는다. 공유 계약이 커밋되지 않았다면 분할을 늦춘다.
- `.env` 같은 미추적 환경 파일, DB 파일, 포트는 자동 공유/격리되지 않는다. 필요한 것은 각 환경에 맞춰 준비한다.
- 테스트 DB와 로컬 서버 포트가 충돌하지 않게 한다. 같은 DB에 병렬 마이그레이션을 실행하지 않는다.
- **제출하는 루트에서** 최종 실행한다. 작업자 워크트리에서만 돌아가는 코드는 미통합이다.
- 분기·머지 자체가 목적이 아니다. 충돌과 설정 복제 비용이 커지면 단일 작업공간과 파일 소유 규칙으로 단순화한다.

## 5분 보고는 퍼센트 대신 증거

추천 보고 형식:

```text
[경과 35분 / 잔여 85분]
완료: R01 업로드→검증→조회 연결, 실제 요청 3개 확인
진행: T03 용량 오류 처리(담당 A), T04 결과 표(담당 B)
막힘: R04 중복 식별자의 업무 의미 미확인 → 해당 집계만 보류
위험: DB 영속성 미검증
다음: T03 통합 후 실패 입력 확인, 실행 환경 재시작 후 재조회
```

“80% 완료”보다 어떤 최종 행동이 되는지가 중요하다. 5분을 기다리지 말아야 할 사건은 필수 규칙 모순, 실패 테스트, 공통 계약 변경, 작업 중단이다. 보고를 기다리는 동안 메인도 독립 구현·통합을 계속한다. 도구가 정확한 타이머를 보장하지 않으면 대략적인 체크포인트로 운영하며 스케줄러 개발을 추가하지 않는다.

## 검토·수정 루프

검토자는 처음부터 계속 감시하지 않는다. 아직 수정 중인 파일을 읽으면 곧 사라질 문제에 의견을 내고 구현자가 계속 방향을 바꿀 수 있다. 완료된 작업 묶음과 고정된 변경 범위를 준다.

```text
새 검토 에이전트로 현재 구현을 읽기 전용 검토해라.
대상은 [기준 커밋→현재 변경]과 관련 미추적 코드, 요구 R01~R04다.
공식 요구·대표 입력·실패 정책과 실제 파일·검사 결과를 대조해라.
요구 누락, 잘못된 계산, 상태/동시성 문제, 데이터 유실, 실행·배포 실패를 우선해라.
취향 리팩터링이나 새 기능은 별도 제안으로 분리해라.
각 문제는 심각도, 요구 ID, 파일:줄, 재현 입력, 기대/실제, 최소 수정안을 반환해라.
재현 못 한 우려는 추정으로 표시하고 직접 코드를 수정하지 마라.
```

메인은 피드백을 세 갈래로 나눈다: **필수 요구 위반은 수정**, **실제 큰 위험은 시간 안에 최소 대응**, **범위 밖 개선은 한계에 기록**. 작업자가 무조건 모든 리뷰 의견을 구현하게 하지 않는다. 채택한 문제는 원 구현자가 수정하고, 검토자가 관련 반례와 영향 범위를 다시 확인한다.

핵심 위험은 해결될 때까지 확인하되, 무한 재설계 루프는 막는다. 같은 유형의 의견이 반복되면 메인이 요구·계약을 다시 확정한다. 최종 검토는 개별 모듈 통과와 별개로 **입력→최종 결과, 설정 변경→재계산, 재시작→재조회** 중 요구되는 흐름을 본다.

## 기록 전담 에이전트에 대한 판단

이 규모에서는 상시 전담을 두지 않는 편을 권한다. 기록자는 당시 결정을 직접 하지 않았으므로 나중에 그럴듯한 이유를 만들어낼 수 있고, 코드와 기록을 동기화하는 일도 추가된다.

대신 다음처럼 책임을 나눈다.

| 기록 | 작성 책임 | 갱신 시점 |
|---|---|---|
| 요구·상태·공통 결정 | 메인 단독 | 요구 변경, 작업 통합 시 |
| 작업별 선택·검사·실패 | 해당 구현자 | 반환 보고 시 |
| 재현 가능한 결함 | 검토자 | 완료된 묶음 검토 시 |
| 실제 코드와 최종 설명의 일치 | 마지막 문서 검토자(선택) | 제출 전 한 차례 |

예외적으로 긴 과제·많은 실무자 대화·여러 데이터 흐름 때문에 메인이 기록에 자주 막히면 기록 보조가 유용할 수 있다. 그래도 그 보조는 작업자 보고를 요약한 초안만 만들고, 공통 정본의 최종 확정은 메인이 한다. 받은 답변·실행 결과·과거 의도를 추측해서 채우지 않는다.

기록량은 활동량에 비례시키지 않는다. **중요 결정마다 선택·이유·검증·한계 4줄**이면 출발점으로 충분하다.

## 최종 10~15% 시간: 구현 설명으로 전환

새 기능을 줄이고 [프로젝트 설명 양식](../templates/PROJECT_DEFENSE.md)을 실제 코드로 채운다. 메인이 설명 초안을 만들고 독립 검토자는 파일·실행 근거와 모순되는 주장만 찾는다.

```text
지금부터 실제 구현 설명을 준비해라.
새 기능은 추가하지 말고 현재 코드·의존성·실행/배포 기록을 읽어라.
1. 실제 실행·배포 위치와 확인한 주소
2. 실제 사용하는 외부 패키지와 내부 모듈의 역할
3. 버튼 하나의 입력→검증→계산→저장→표시 흐름
4. 알고리즘 선택 이유·대안·최적성 보장 여부
5. 설정/DB 변경과 계산 실패 시 현재 동작
6. 가정·미구현·미검증·개선안
각 항목을 쉬운 설명과 파일:함수 근거로 정리해라.
구현한 것과 개선 제안을 문단부터 분리하고, 실행하지 않은 성능 수치를 만들지 마라.
그다음 답을 가린 질문 5개로 내가 직접 설명하는 사전 리허설을 진행하자.
```

## 전체 스킬을 다 깔지 않는 이유

여러 프레임워크가 계획·인터뷰·TDD·리뷰를 각각 강제하면 같은 단계가 중복되고 지침이 충돌할 수 있다. 공식 OpenAI 글도 많은 스킬의 긴 설명과 과도한 적용 범위가 문맥 부담과 충돌을 만들 수 있다고 설명한다. 필요한 진입점과 참고 파일을 선택하는 구성이 낫다. [공식 프롬프트·스킬 설계 글](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)
