# 직전 복습: 프로젝트에서 바로 확인할 12가지

이 페이지는 사전 연습용이다. `[ ]`는 실제 과제에서 채울 값이며, 예시 기술을 사용 사실로 읽지 않는다.

## 답변의 기본 순서

> 현재는 **[실제 방식]**으로 구현했습니다. **[입력 크기·요구·환경]** 때문에 선택했고, **[파일:함수]**에서 처리합니다. **[직접 실행한 검사와 결과]**로 확인했습니다. 다만 **[한계]**가 있어, **[조건]**이 되면 **[개선]**하겠습니다.

예상했던 이유와 개발 당시 실제 이유가 다르면 구분한다. 성능을 재지 않았으면 “빨라서” 대신 “구현 복잡도를 줄이려고 선택했고, 성능 비교는 하지 못했습니다”라고 답한다.

## 1. 배포는 뭘로 했나요?

**제공 환경에서만 실행했다면:**

> 제공된 실행 환경에서 [실제 명령]으로 [포트]에 실행하고 [미리보기/공개 접근 주소]에서 확인했습니다. 별도 클라우드 배포는 하지 않았습니다. 데이터는 [실제 저장 위치]에 저장하므로 [프로세스/환경 초기화] 시 보존 범위는 [확인 결과/미확인]입니다.

**실제 외부 배포했다면:**

> 프론트는 [서비스], API는 [서비스/동일 서비스], DB는 [서비스]를 썼습니다. [커밋/빌드]가 [빌드 명령]을 거쳐 배포되고, [URL]에서 입력→저장→재조회까지 확인했습니다. [환경변수 이름]은 서버 설정으로 주입했습니다. 장시간 계산은 [실제 처리 방식]이고 [제한]이 남습니다.

Docker는 패키징 방식, Uvicorn은 Python ASGI 서버, Nginx는 프록시 역할이다. 이 이름만으로 호스팅 위치를 답한 것이 아니다.

## 2. 백엔드에서 어떤 모듈을 썼나요?

> 외부 패키지는 [API 프레임워크: 요청 처리], [검증 패키지: 형식·범위 검증], [DB 패키지: 조회·저장]입니다. 프로젝트 내부는 [라우터]→[업무 서비스]→[계산 모듈/저장소]로 연결됩니다. [실제 import와 호출 위치]에서 확인할 수 있습니다.

의존성 파일에만 있는 패키지는 실제 호출한 패키지와 구분한다. Node 풀스택이면 Python 백엔드를 꾸며내지 않는다.

## 3. 데이터 흐름을 설명하세요

> 사용자가 [입력]하면 [컴포넌트]가 [API]로 보냅니다. 서버가 [검증]하고 [DB/파일]에서 [기준 데이터]를 읽습니다. [서비스 함수]가 [계산]한 뒤 [결과 저장 위치]에 기록하고 [응답]을 반환합니다. 화면은 [응답/조회 API]로 결과를 표시합니다. 실패 시 [실제 처리]합니다.

실제 DB가 없으면 “메모리/파일에서 읽는다”고 말한다. 버튼 하나를 기준으로 파일과 함수를 따라가며 설명한다.

## 4. 왜 휴리스틱인가요?

> 최적화 대상은 [목적함수], 반드시 지킬 조건은 [제약]입니다. [실제 사용한 탐욕·삽입·교환 등]으로 해를 만들었습니다. 선택 이유는 [실제 제약]이고, 전역 최적성은 보장하지 않습니다. [기준선/작은 정답]과 [실측 수치]로 비교했습니다. 비교하지 않았다면 현재 품질은 미검증이라고 답하겠습니다.

“NP-hard라서 정확해법이 불가능하다”는 답은 피한다. 작은 규모에서는 정확해법이 충분할 수 있고, 제한시간을 둔 솔버도 대안이다.

## 5. 운영자가 용량·처리 시간을 바꾸면요?

> [실제 설정 위치]를 [검증·권한 검사] 후 변경합니다. 진행 중 계산은 [시작 시점 설정 고정/취소 후 재계산/미지원] 정책입니다. 결과에는 [기준 버전 표시 여부]가 있고, 기존 결과의 적용은 [재검증 여부]로 판단합니다. 아직 코드에 없다면 그 부분을 개선안으로 설명합니다.

설정값을 파일로 뺀 것만으로 실행 중 안전한 변경이 구현되지는 않는다. 캐시·이미 저장된 결과·동시 수정까지 영향받는다.

## 6. 계산 중 DB가 바뀌면요?

> 매번 최신 값을 다시 읽으면 구버전과 신버전이 섞일 수 있습니다. 제안 설계는 짧고 일관된 읽기로 입력 스냅샷을 만들고, 계산 동안 그 복사본을 쓰는 것입니다. 계산 결과를 저장할 수는 있어도, 현재 운영에 적용할 때는 관련 데이터·설정 버전을 같은 트랜잭션에서 확인해야 합니다. 다르면 재계산하거나 적용을 거절합니다.

한 번의 HTTP 요청이라는 사실이나 트랜잭션을 썼다는 사실만으로 계산 전체의 일관성이 보장되지는 않는다.

## 7. 한 번 요청하고 계속 기다리면 뭐가 문제인가요?

> 응답 시간 초과가 나도 서버 계산은 계속될 수 있어 성공 여부가 불명확해지고, 재요청으로 작업이 중복될 수 있습니다. 진행 상태·취소·복구도 어렵습니다. 짧고 상한이 확인된 작업이면 동기 처리로 단순하게 갈 수 있지만, 긴 작업은 작업 ID를 먼저 반환하고 상태를 조회하는 구조가 적절합니다. 비동기화와 별개로 입력 버전과 중복 처리 방지가 필요합니다.

화면의 `await fetch()`는 서버 작업 큐의 증거가 아니다. `async def`도 무거운 CPU 계산을 자동 병렬 처리하지 않는다.

## 8. 중간에 계산 오류가 나면요?

> [현재 예외 처리]가 동작합니다. 개선할 경우 작업을 FAILED로 남기고 원인 코드·재시도 가능 여부를 기록합니다. 결과와 SUCCEEDED 상태는 한 트랜잭션으로 저장하고, 강제 종료는 heartbeat/lease 만료로 감지합니다. 재시도는 같은 입력 스냅샷으로 수행하고 중복 결과가 생기지 않게 합니다.

## 9. 추가 가정은 뭔가요?

> [가정]은 문제에 명시되지 않아 [이유]로 정했습니다. 이 가정이 바뀌면 [함수/설정/검증 기준]을 수정해야 합니다. [확인받은 내용]은 가정과 구분해 기록했습니다.

시간 단위, 시간대, 동점 처리, 결측값 의미, 중복 식별자, 최대/정확히/최소 수, 해가 없을 때 정책을 떠올린다.

## 10. 결과를 어떻게 믿나요?

> 손으로 검산 가능한 [작은 사례], 반드시 지켜야 할 [불변조건], [실제 요구의 경계값]을 확인했습니다. [테스트 실행 수·실패 여부]가 근거입니다. 환경 점검 통과와 업무 정답 검증은 구분합니다.

## 11. AI에게 무엇을 맡겼나요?

> [실제 작업]을 맡겼고, [규칙/우선순위/대안 선택]은 제가 결정했습니다. [실제 확인한 오류]를 [검증]으로 발견해 [수정]했습니다. 그런 사건이 없었다면 AI 오류를 발견했다고 꾸미지 않습니다.

## 12. 시간이 더 있으면 무엇부터 바꾸나요?

> 현재 가장 큰 위험은 [구체적 실패]입니다. 먼저 [작은 개선]을 해 [실패 재현 테스트]로 확인하겠습니다. 이후 사용량이 [조건]을 넘으면 [확장]하겠습니다.

기술을 늘어놓기보다 사용자 피해가 가장 큰 한 가지를 먼저 고른다.
